# SSR and Initial State

## Initial snapshots define hydration

SSR support in `@ilokesto/state` comes from the same contract that powers the hook in the browser.
The hook is built around React's external store subscription model, so React can ask the store for one snapshot while rendering on the server and another snapshot while running on the client.

That sounds small, but it decides whether hydration feels predictable.
The server renders markup from a value.
The client then attaches event handlers to that markup and checks the first client read against what the server already produced.
If those values are not aligned, React can report a hydration mismatch or replace part of the rendered tree.

The useful rule is this:

- `getState()` answers, "What is the store value right now?"
- `getInitialState()` answers, "What value did this store start with?"

Those are different questions.
A store can start with `{ count: 0 }`, receive a write, and then report `{ count: 1 }` from `getState()`.
Its initial value is still `{ count: 0 }`.

`@ilokesto/state` uses `store.getInitialState()` for the server snapshot path.
That keeps server rendering tied to the constructor time value instead of to later client side mutations.
When you design SSR code, treat the initial value as part of the render contract, not just as a convenient default.

## Server and client snapshots

React's external store contract has two snapshot reads that matter here.
The client snapshot is the live value used after the app is running.
The server snapshot is the value React uses while rendering HTML on the server and while checking the first hydration pass.

In `@ilokesto/state`, the distinction maps cleanly to the store methods:

```ts lineNumbers
const useCounter = create({ count: 0 });

const current = useCounter.getState();
const initial = useCounter.getInitialState();
```

`getState()` returns the current live value.
It changes after writes.
Use it for event handlers, actions, effects, tests, and any code that needs the latest store value.

`getInitialState()` returns the value captured when the store was created.
It does not become a second live store.
It is a stable description of the starting point.

During SSR, the hook provides `store.getInitialState()` as the server snapshot.
That means a component rendered on the server should see the same shape and values that the store was created with for that request.
If the client creates the store with the same initial data, hydration starts from the same snapshot.

This is why initial data must be explicit.
If the server creates a store from request data, the client needs the same serialized request result when it creates its matching store.
Do not depend on a client effect to "catch up" after hydration.
Effects run too late to protect the first render.

## Per-request stores

Server code handles many users over the life of one process.
That makes module level state dangerous in SSR.
A singleton store can accidentally keep data from request A and expose it while rendering request B.

This is safe in a browser tab because the module belongs to one user session.
It is not safe as a default server pattern because the module can be shared across requests.

Prefer a factory that creates a new store for each request:

```ts lineNumbers
import { create } from '@ilokesto/state';

type ViewerState = {
  viewerId: string | null;
  theme: 'light' | 'dark';
};

export function createViewerStore(initialState: ViewerState) {
  return create(initialState);
}
```

Then call the factory from request scoped code:

```tsx lineNumbers
import { createViewerStore } from './viewer-store';

type PageProps = {
  viewer: {
    id: string;
    theme: 'light' | 'dark';
  } | null;
};

export default function Page({ viewer }: PageProps) {
  const initialState = {
    viewerId: viewer?.id ?? null,
    theme: viewer?.theme ?? 'light',
  };

  const useViewer = createViewerStore(initialState);

  return <ViewerPanel useViewer={useViewer} />;
}
```

This example avoids inventing a framework adapter.
It only shows the important boundary: request data becomes an initial object, and that object is passed into `create()` through a factory.

The wrong shape is a server singleton that is reused for every request:

```ts lineNumbers
import { create } from '@ilokesto/state';

export const useViewer = create({
  viewerId: null,
  theme: 'light',
});
```

That singleton can be fine for purely client side state.
For server rendering with user specific data, it creates a leak risk.
One request can write the store before another request renders.
Even if you never write during render, future maintenance can turn the singleton into a shared mutable cache by accident.

## Hydration and mismatch

Hydration compares the server rendered result with the first client render.
The safest path is boring: create the client store with the same initial state that produced the server markup.

This works:

```tsx lineNumbers
const initialState = {
  viewerId: 'user-123',
  theme: 'dark',
};

const useViewer = create(initialState);
```

This is risky:

```tsx lineNumbers
const useViewer = create({
  viewerId: null,
  theme: 'light',
});

useViewer.setState({
  viewerId: 'user-123',
  theme: 'dark',
});
```

The second example may reach the right live state, but it does not start from the same snapshot.
The first render can show anonymous light mode markup while the server produced signed in dark mode markup.
React sees a different tree before your correction has a chance to settle.

The same issue can appear when reading browser only data during the initial render.
For example, a theme stored in `localStorage` is not available during server rendering.
If server markup assumes `light` and the first client render assumes `dark`, the app starts with two different answers.

Pick one source for the first render.
If the server owns the first answer, serialize that answer and create the client store from it.
If the browser owns the first answer, render a stable placeholder until the browser value is known.
Do not mix the two without an explicit rule.

## Bootstrap pattern

A bootstrap pattern makes the initial value visible at the boundary between server and client.
The server prepares plain JSON.
The client reads that JSON and passes it into the same store factory.

With a Next.js style setup, the shape can stay simple:

```tsx lineNumbers
// app/account/page.tsx
import { AccountClient } from './account-client';

export default async function AccountPage() {
  const viewer = await loadViewerForRequest();

  const initialState = {
    viewerId: viewer?.id ?? null,
    displayName: viewer?.displayName ?? 'Guest',
  };

  return <AccountClient initialState={initialState} />;
}
```

```tsx lineNumbers
// app/account/account-client.tsx
'use client';

import { create } from '@ilokesto/state';

type AccountState = {
  viewerId: string | null;
  displayName: string;
};

type AccountClientProps = {
  initialState: AccountState;
};

export function AccountClient({ initialState }: AccountClientProps) {
  const useAccount = create(initialState);

  return <AccountView useAccount={useAccount} />;
}
```

The example uses normal component props as the bootstrap channel.
It does not require a package specific provider or hidden global.
The key is that `initialState` is a plain object that can cross the server to client boundary safely.

For larger apps, keep the factory separate from the framework file:

```ts lineNumbers
import { create } from '@ilokesto/state';

export type AccountState = {
  viewerId: string | null;
  displayName: string;
};

export function createAccountStore(initialState: AccountState) {
  return create(initialState);
}
```

That gives tests, server files, and client files one shared way to create the store.
It also makes the initial state type explicit, which helps prevent the server and client from drifting apart.

## Persistence + SSR conflict

Persistence adds another first render question.
The server can provide one initial state, while the browser has an older persisted state from a previous visit.
Both values can be valid, but they cannot both own hydration at the same time.

Imagine the server renders this:

```ts lineNumbers
const serverInitialState = {
  viewerId: 'user-123',
  displayName: 'Ari',
};
```

The browser may have this stored locally:

```ts lineNumbers
const persistedState = {
  viewerId: 'user-123',
  displayName: 'Old Name',
};
```

If persistence replaces the store before hydration, the client can render `Old Name` while the server markup says `Ari`.
That is a mismatch even though both states belong to the same user.

Choose a precedence rule before wiring persistence into an SSR page:

1. Server initial state wins for hydration, then persisted state may merge later.
2. Persisted state wins only after a client only gate renders a stable fallback.
3. Certain fields come from the server, while local preferences come from persistence.

The first rule is usually safest for request scoped data such as identity, permissions, and server loaded records.
The third rule works well for local preferences such as collapsed panels or draft UI settings.

Keep the split explicit:

```ts lineNumbers
type AccountState = {
  viewerId: string | null;
  displayName: string;
  sidebarCollapsed: boolean;
};
```

In that shape, `viewerId` and `displayName` can come from the server initial state, while `sidebarCollapsed` can be restored after the client starts.
The point is not that persistence is incompatible with SSR.
The point is that persisted state is another source of truth, so it needs a clear timing and precedence rule.

When the rule is unclear, use `getInitialState()` as the anchor for the server rendered snapshot and delay persisted overrides until after hydration.
That keeps the first client render aligned with the server output and still lets the browser restore local preferences once React is in control.
