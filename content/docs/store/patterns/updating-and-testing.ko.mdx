# 업데이트와 테스트

스토어의 소유자가 정해졌다면 다음 단계는 업데이트를 예측 가능하게 유지하는 것입니다. 가장 안전한 패턴은 단순합니다: 상태를 의도적으로 교체하고, 부가 값은 저장된 값 밖에서 파생하고, 테스트마다 새 스토어를 만드세요.

## 초기화 패턴

`getInitialState()`는 생성자에 전달한 값을 반환합니다. 그래서 reset helper를 단순하게 만들 수 있지만, `Store`는 런타임에서 그 값을 복제하거나 동결하지 않는다는 점을 기억해야 합니다.

```ts lineNumbers
import { Store } from "@ilokesto/store";

type FormState = {
  name: string;
  email: string;
  submitted: boolean;
};

const formStore = new Store<FormState>({
  name: "",
  email: "",
  submitted: false,
});

export function resetForm() {
  formStore.setState(formStore.getInitialState());
}
```

초기값에 앱 코드가 바꿀 수 있는 중첩 객체가 있다면, 같은 참조를 다시 쓰기보다 팩토리로 새 초기값을 만드세요.

```ts lineNumbers
function createInitialFormState(): FormState {
  return { name: "", email: "", submitted: false };
}

const formStore = new Store<FormState>(createInitialFormState());

export function resetForm() {
  formStore.setState(createInitialFormState());
}
```

## 파생 값

`Store`는 하나의 소스 값을 보관합니다. 부가 값은 일반 함수로 파생하면 항상 최신 스냅샷을 기준으로 계산됩니다.

```ts lineNumbers
type CartState = {
  items: Array<{ id: string; price: number; quantity: number }>;
};

const cartStore = new Store<CartState>({ items: [] });

export function getCartTotal() {
  return cartStore
    .getState()
    .items.reduce((sum, item) => sum + item.price * item.quantity, 0);
}

export function hasItems() {
  return cartStore.getState().items.length > 0;
}
```

사용자 입력으로 보존해야 하는 값이 아니라면 파생 데이터를 저장된 상태 밖에 두세요. 이렇게 하면 업데이트 뒤에 오래된 캐시 필드가 남는 일을 피할 수 있습니다.

## 비동기 흐름

비동기 작업은 스토어 업데이트 주변에서 처리하세요. 요청을 시작하고 loading 상태를 업데이트한 다음, 요청이 끝나면 전체 상태를 교체합니다.

```ts lineNumbers
type ProfileState = {
  profile: { id: string; name: string } | null;
  loading: boolean;
  error: string | null;
};

const profileStore = new Store<ProfileState>({
  profile: null,
  loading: false,
  error: null,
});

export async function loadProfile(userId: string) {
  profileStore.setState((prev) => ({
    ...prev,
    loading: true,
    error: null,
  }));

  try {
    const profile = await fetchProfile(userId);

    profileStore.setState({
      profile,
      loading: false,
      error: null,
    });
  } catch (error) {
    profileStore.setState((prev) => ({
      ...prev,
      loading: false,
      error: error instanceof Error ? error.message : "Unknown error",
    }));
  }
}
```

`setState` 자체는 동기식입니다. 비동기 부분은 Store 알림 모델이 아니라 그 주변의 사용자 함수에 있습니다.

Store는 서버 캐시 라이브러리도 아닙니다. retry, 요청 deduplication, invalidation, stale-time 동작이 필요하다면 data-fetching 도구와 함께 사용하고, Store는 클라이언트가 직접 소유한 상태에 집중시키세요.

## 격리된 스토어로 테스트하기

테스트는 각 테스트가 팩토리를 통해 자기 스토어를 만들 때 가장 쉽습니다.

```ts lineNumbers
import { expect, test } from "vitest";

test("increments count", () => {
  const { store, increment } = createCounterStore();

  increment();

  expect(store.getState().count).toBe(1);
});

test("notifies subscribers after a change", () => {
  const { store, increment } = createCounterStore();
  let calls = 0;

  const unsubscribe = store.subscribe(() => {
    calls += 1;
  });

  increment();
  unsubscribe();

  expect(calls).toBe(1);
});
```

테스트가 구독을 만들었다면 테스트가 끝나기 전에 항상 unsubscribe 함수를 호출하세요. 프레임워크 어댑터에서 사용하는 생명주기 정리 규칙과 같은 습관입니다.

## 흔한 실수

- `getState()`에서 받은 객체를 직접 바꾸지 마세요. 상태를 새 값으로 교체하세요.
- 객체 업데이트를 병합처럼 다루지 마세요. 객체 업데이트는 전체 상태를 교체합니다.
- guard 없이 subscriber 안에서 `setState`를 호출하지 마세요. 동기식 루프가 생길 수 있습니다.
- 격리된 상태를 기대하는 테스트 사이에서 하나의 모듈 수준 스토어를 공유하지 마세요.
