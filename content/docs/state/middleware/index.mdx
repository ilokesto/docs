# Middleware

`@ilokesto/state` middleware does not wrap React components. It wraps the underlying store, so extensions can change how updates move through the store before React sees the result.

All built-in middleware are available from the `@ilokesto/state/middleware` entry point, and they are designed to compose cleanly with `pipe()`.

```ts lineNumbers
import { create } from '@ilokesto/state';
import { logger, persist } from '@ilokesto/state/middleware';
import { pipe } from '@ilokesto/state/utils';

const useStore = create(
  pipe(
    { count: 0 },
    logger(),
    persist({ local: 'my-app-storage' })
  )
);
```

## Composition Pattern

Most middleware support two calling styles:
1. **Direct**: `middleware(store, options)`
2. **Curried**: `middleware(options)(store)`

The curried form reads cleanly when a store is composed declaratively.

## Built-in Middleware

Each middleware does a different job at the store layer:

- [**Logger**](./logger): Logs state changes to the console.
- [**DevTools**](./devtools): Connects your store to Redux DevTools.
- [**Persist**](./persist): Synchronizes state with `localStorage`, `sessionStorage`, or cookies.
- [**Debounce**](./debounce): Batches rapid updates into one delayed flush window.
- [**Validate**](./validate): Validates state updates using Standard Schema v1.

## Execution Order

`pipe()` applies middleware from top to bottom, or left to right in the call. That order changes the update path.

For example, placing `logger()` before `debounce()` logs every attempted update, while placing it after logs only the delayed flush result.

If you use one middleware, start with its page. If you compose several, choose the order before tuning each feature.
