# Accessors

Accessors are static methods attached to the adapter returned by `create`. Start with `writeOnly()` when action files, listeners, or other imperative code need to update state. Use `readOnly()` when non-rendering code needs a synchronous snapshot.

## `writeOnly()`

`writeOnly()` is the canonical imperative writer. It returns the store's `setState` function (or `dispatch` if using a reducer).

- **Outside framework lifecycles**: This is the preferred way to define actions, side effects, or event listeners.
- **Inside components**: Use the adapter directly when a component should subscribe to state and re-render from selector changes.

Each `writeOnly()` call returns a bound store writer. The important stability is behavioral, not referential: it always points at the same underlying store.

```ts lineNumbers
const useCounter = create({ count: 0 });

// Ideal for standalone action files
export const increment = () => {
  const setState = useCounter.writeOnly();
  setState(state => ({ count: state.count + 1 }));
};
```

This keeps action modules small and direct: import the adapter, call `writeOnly()`, then write through the returned function.

## `readOnly()`

`readOnly()` returns the current store snapshot, optionally projected through a selector. It is a synchronous read helper and does not subscribe the caller to future updates.

```tsx lineNumbers
export function getCurrentCount() {
  return useCounter.readOnly((state) => state.count);
}
```

If the value affects rendered output, prefer the framework adapter with a selector so the component can subscribe and update normally.

## When to use the vanilla `Store` instead

If non-framework code already owns the store directly, the vanilla `Store` API from `@ilokesto/store` is still the clearest imperative boundary.

The pattern for this is to create the store separately and pass it to `create()`:

```ts lineNumbers
import { Store } from '@ilokesto/store';
import { create } from '@ilokesto/state/react';

// 1. Create the vanilla store
export const counterStore = new Store({ count: 0 });

// 2. Create the hook from it
export const useCounter = create(counterStore);

// 3. You can still read through the owned vanilla store directly.
export const checkCount = () => {
  console.log(counterStore.getState().count);
};
```

## Action-file patterns

A common architectural pattern is to keep stores and actions separate. Accessors make this clean:

```ts lineNumbers
// stores/auth.ts
export const useAuth = create({ user: null, loading: false });

// actions/auth.ts
import { useAuth } from '../stores/auth';

export const login = async (credentials) => {
  const setState = useAuth.writeOnly();
  setState((prev) => ({ ...prev, loading: true }));
  const user = await api.login(credentials);
  setState((prev) => ({ ...prev, user, loading: false }));
};
```

Keep this pattern focused on writes. If an action file also needs to inspect current state, use `readOnly()` for a quick snapshot or define the vanilla `Store` separately and read through `store.getState()` when ownership should stay outside the adapter.

## Common mistakes

1. **Expecting `readOnly()` to subscribe**: It returns a snapshot. It does not update a component when the store changes.
2. **Ignoring adapter return shapes**: React returns a tuple, Vue/Solid/Angular return objects, and Svelte returns store-like objects.
3. **Overusing `readOnly()` inside components**: If you need the value for rendering, use the adapter directly with a selector.
