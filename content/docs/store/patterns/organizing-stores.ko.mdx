# 스토어 조직하기

스토어 구조는 한 가지 질문에서 시작하면 쉽습니다: 이 상태의 소유자는 누구인가요?

앱 전체가 공유한다면 모듈 수준 스토어가 단순합니다. 화면, 탭, 요청, 테스트마다 자기 복사본이 필요하다면 팩토리를 사용하세요. 서로 관련 없는 필드가 서로 다른 이유로 바뀐다면 별도 스토어로 나누세요.

## 모듈 수준 스토어

앱의 여러 부분이 공유해야 하는 상태에는 모듈 수준 스토어가 잘 맞습니다. 상태 모양은 좁게 유지하고, 허용되는 업데이트를 설명하는 작은 함수를 함께 내보내세요.

```ts lineNumbers
import { Store } from "@ilokesto/store";

type AuthState = {
  user: { id: string; name: string } | null;
  status: "anonymous" | "signed-in";
};

const initialAuthState: AuthState = {
  user: null,
  status: "anonymous",
};

export const authStore = new Store<AuthState>(initialAuthState);

export function signIn(user: { id: string; name: string }) {
  authStore.setState({ user, status: "signed-in" });
}

export function signOut() {
  authStore.setState(initialAuthState);
}
```

auth, theme, feature flag, 현재 workspace처럼 앱 전체에서 공유되는 작은 값에 이 패턴을 사용하세요.

## 스토어 팩토리

팩토리는 기능 인스턴스마다 새 스토어를 만듭니다. 사용자, 화면, 탭, 테스트, 서버 요청 범위 사이에 상태가 새면 안 될 때 유용합니다.

```ts lineNumbers
import { Store } from "@ilokesto/store";

type CounterState = {
  count: number;
};

export function createCounterStore(initialCount = 0) {
  const store = new Store<CounterState>({ count: initialCount });

  return {
    store,
    increment() {
      store.setState((prev) => ({ count: prev.count + 1 }));
    },
    decrement() {
      store.setState((prev) => ({ count: prev.count - 1 }));
    },
  };
}
```

모듈 수준 스토어 때문에 테스트 순서가 결과에 영향을 주거나 앱 인스턴스 사이에 상태가 의도치 않게 공유된다면 팩토리를 선택하세요.

## 스토어 나누기

서로 관련 없는 소비자가 같은 알림 흐름을 공유하면 안 될 때는 책임별로 스토어를 나누세요.

```ts lineNumbers
import { Store } from "@ilokesto/store";

export const themeStore = new Store<"light" | "dark">("light");

export const sessionStore = new Store({
  userId: null as string | null,
  activeWorkspaceId: null as string | null,
  tokenExpiresAt: null as number | null,
});

export const draftStore = new Store({
  title: "",
  body: "",
});
```

분리된 스토어는 소유권을 더 분명하게 만듭니다. 각 스토어가 하나의 일을 맡기 때문에 초기화와 테스트도 작아집니다.

## 하나의 거대한 스토어 피하기

앱 전체를 담는 단일 객체는 편해 보이지만, 시간이 지나면 안전하게 바꾸기 어려워지는 경우가 많습니다.

다음 신호를 살펴보세요.

- 관련 없는 업데이트에도 많은 필드를 spread해야 합니다.
- 작은 동작을 테스트하려고 큰 fixture가 필요합니다.
- 구독자가 관심 없는 변경에도 깨어납니다.
- reset 로직이 모든 기능을 알아야 합니다.

대신 domain마다 스토어를 두세요. 두 domain이 함께 움직여야 한다면, 각 스토어를 명시적으로 업데이트하는 앱 수준 함수를 작성합니다.

```ts lineNumbers
export function clearWorkspace() {
  sessionStore.setState((prev) => ({ ...prev, activeWorkspaceId: null }));
  draftStore.setState({ title: "", body: "" });
}
```

이렇게 하면 모든 기능을 하나의 공유 상태 객체로 합치지 않고도 조정 지점을 코드에 드러낼 수 있습니다.
