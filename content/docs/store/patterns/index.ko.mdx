# 공통 패턴

이 섹션은 첫 스토어가 동작한 다음, “실제 앱에서는 이걸 어떤 모양으로 잡아야 하지?”라는 질문이 생길 때 읽는 곳입니다.

`@ilokesto/store`는 의도적으로 작게 유지됩니다. 하나의 값, 교체 업데이트, 구독만 제공합니다. 여기의 패턴들은 이 조각들을 프레임워크, reducer 시스템, data-fetching cache로 키우지 않고 앱 코드에 맞게 배치하는 방법을 보여줍니다.

## 어디로 가면 될까요?

- [스토어 조직하기](./organizing-stores) — 모듈 수준 스토어, 스토어 팩토리, 여러 작은 스토어 중 무엇을 고를지 정합니다.
- [업데이트와 테스트](./updating-and-testing) — 상태 초기화, 파생 값, 비동기 흐름, 격리된 테스트를 다룹니다.

`Store` 위에 프레임워크 어댑터나 라이브러리를 만드는 중이라면 [Store 기반 구축하기](../building-on-store)에서 시작하세요. 정확한 교체, 구독, 베일아웃 규칙이 필요하다면 [고급 시맨틱](../advanced-semantics)을 보세요.

## 작은 기준 하나

소유자가 분명한 가장 작은 스토어에서 시작하세요.

```ts lineNumbers
import { Store } from "@ilokesto/store";

export const themeStore = new Store<"light" | "dark">("light");

export function toggleTheme() {
  themeStore.setState((prev) => (prev === "light" ? "dark" : "light"));
}
```

여러 화면에서 공유해야 하는 상태라면 모듈 수준에 둡니다. 화면, 탭, 요청, 테스트마다 자기 복사본이 필요하면 팩토리를 사용합니다. 서로 관련 없는 부분이 독립적으로 바뀐다면 별도 스토어로 나눕니다.

## Store가 해결하려 하지 않는 것

이 레시피들은 Store를 클라이언트 애플리케이션 상태에 집중시킵니다. 서버 캐시, retry, invalidation, 요청 deduplication이 필요하다면 그런 기능을 상태 객체 안에 다시 만들기보다 data-fetching 도구와 함께 사용하세요.

Store는 앱이 직접 소유하는 값에 잘 맞습니다: theme, 현재 draft, auth snapshot, feature flag, 작은 workflow 상태, 로컬 UI 조각 사이의 조정 값 같은 것들입니다.
