# Patterns

The APIs are small, but the way they compose matters. This page covers the patterns that tend to survive first contact with a real product.

## Promise toasts

The most common higher-level pattern is `toast.promise()`.

```ts
toast.promise(fetchData(), {
  loading: 'Fetching data...',
  success: (data) => `Loaded ${data.name}`,
  error: 'Could not fetch data.',
});
```

The runtime reuses the same toast id across loading -> success/error.

That keeps the stack quiet. Users do not need one toast for “starting”, another for “done”, and a third for failure; they need one evolving status surface.

## Per-toast styling

```ts
toast.success('Deleted!', {
  style: { background: 'red', color: 'white' },
  iconTheme: { primary: 'white', secondary: 'red' },
});
```

This is the right level when only one toast needs a custom look.

If you find yourself repeating this setup for a whole feature, move the defaults up into `toastOptions` instead of styling each call site independently.

## Multiple toasters

```tsx
<>
  <Toaster toasterId="app" position="top-right" />
  <Toaster toasterId="editor" position="bottom-center" />
</>

toast.success('Saved', { toasterId: 'editor' });
```

Each `toasterId` gets an independent runtime.

That separation is useful when one part of the UI should not compete with another. An editor footer, for example, can keep its own notifications without being swallowed by an app-wide stack.

## Dismiss all vs remove all

```ts
toast.dismiss();
toast.remove();
```

Omitting the id applies the action to all active toasts for that runtime.

Use `dismiss()` when you want the exit motion to play. Use `remove()` when you intentionally want a hard cut.

## Custom rows through `Toaster`

```tsx
<Toaster>
  {(toast, { dismiss }) => (
    <button onClick={dismiss}>{toast.message}</button>
  )}
</Toaster>
```

Use this when row-level control matters more than the default presentation.

## A practical rule of thumb

- Stay with the default renderer until a product requirement forces a different row layout.
- Use `toastOptions` for shared defaults.
- Use per-toast `style` and `iconTheme` when the variation is rare and local.
- Introduce multiple `toasterId` values only when the UI truly has separate notification surfaces.
