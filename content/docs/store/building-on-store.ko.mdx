# 스토어 기반 구축하기

`@ilokesto/store` 위에 프레임워크 어댑터, 재사용 라이브러리, controller, 통합 계층을 만들고 있다면 이 페이지를 사용하세요.

이 문서는 작성자용 가이드이며, 앱 코드에 그대로 복사하는 사용법이 아닙니다. 앱 개발자는 React, Vue, Svelte, Angular 예제를 다루는 [프레임워크 사용법](./framework-usage)이나 애플리케이션 레시피를 모은 [공통 패턴](./patterns)에서 시작하는 편이 좋습니다. 이 페이지는 어댑터가 의존할 수 있는 안정적인 경계에 집중합니다.

정확한 메서드 시그니처는 [API 레퍼런스](./api)를 읽으세요. 교체, 동등성, 알림, 리스너 규칙은 [고급 시맨틱](./advanced-semantics)에 있습니다.

## 어댑터 설계 원칙

대상 런타임에 맞는 가장 얇은 브리지를 만드세요.

대부분의 어댑터는 네 가지 일을 합니다.

1. `store.getState()`로 현재 값을 읽습니다.
2. `store.subscribe(listener)`로 구독합니다.
3. `store.setState(next)`나 자체 action 계층으로 쓰기를 전달합니다.
4. 소유 런타임 범위가 끝나면 unsubscribe 함수를 호출합니다.

`Store`를 source of truth로 유지하세요. hook, ref, signal, effect, selector, validation, persistence, devtools 같은 프레임워크별 개념은 프레임워크나 라이브러리 계층이 소유하게 두는 편이 좋습니다.

## 공개 계약 경계

어댑터 코드는 다음 메서드를 경계로 다루세요.

- `getState()`는 현재 스냅샷을 읽습니다.
- `setState(next)`는 상태를 값이나 업데이트 함수 결과로 교체합니다.
- `subscribe(listener)`는 성공한 상태 교체를 관찰하고 cleanup을 반환합니다.
- `getInitialState()`는 추상화가 reset이나 bootstrap 동작을 필요로 할 때 생성자 값을 읽습니다.

어댑터를 private 필드, 리스너 저장소, 미들웨어 배열, 구현 helper 이름에 결합하지 마세요. 라이브러리가 `Store`를 직접 노출한다면 소비자가 vanilla `@ilokesto/store` API를 사용한다는 점을 문서화하세요. 라이브러리가 `Store`를 감싼다면 시간이 지나도 지원할 수 있는 메서드와 action만 노출하세요.

```ts lineNumbers
import { Store } from "@ilokesto/store";

type ReadonlyStore<T> = {
  getState(): Readonly<T>;
  subscribe(listener: () => void): () => void;
};

export function readonlyView<T>(store: Store<T>): ReadonlyStore<T> {
  return {
    getState: () => store.getState(),
    subscribe: (listener) => store.subscribe(listener),
  };
}
```

이런 wrapper는 내부 구현에 의존하지 않고도 라이브러리에서 쓰기를 숨길 수 있게 해 줍니다.

## 생명주기 매핑

각 구독을 대상 런타임의 한 소유자에 매핑하세요. 그 소유자는 component, request, controller, test harness, 오래 사는 service일 수 있습니다.

```ts lineNumbers
import { Store } from "@ilokesto/store";

type StoreConnection<T> = {
  getSnapshot(): Readonly<T>;
  setState(nextState: T | ((prevState: Readonly<T>) => T)): void;
  destroy(): void;
};

export function connectStore<T>(store: Store<T>): StoreConnection<T> {
  let snapshot = store.getState();

  const unsubscribe = store.subscribe(() => {
    snapshot = store.getState();
  });

  return {
    getSnapshot: () => snapshot,
    setState: (nextState) => {
      store.setState(nextState);
    },
    destroy: unsubscribe,
  };
}
```

이 형태의 프레임워크별 버전은 [프레임워크 사용법](./framework-usage)에 속합니다. 작성자 규칙은 모든 런타임에서 같습니다. 소유자가 시작할 때 구독을 만들고, 소유자가 멈출 때 정리합니다.

## 스냅샷 일관성

`getState()`는 권위 있는 스냅샷 reader입니다. 구독 리스너는 캐시된 값을 믿기보다 리스너 안에서 새 스냅샷을 읽어야 합니다.

Store 알림은 성공한 교체 뒤에 동기적으로 발생합니다. 대상 런타임이 업데이트를 batch하거나 schedule한다면, 그 scheduling은 어댑터 계층의 책임입니다. Store 자체를 batched 또는 async라고 설명하지 마세요.

```ts lineNumbers
const unsubscribe = store.subscribe(() => {
  const nextSnapshot = store.getState();
  publishToRuntime(nextSnapshot);
});
```

selector를 추가한다면 동등성 검사가 어디에서 일어나는지 문서화하세요. `Store`는 root state 값에 대해 자체 `Object.is` 베일아웃만 적용합니다. Selector memoization은 core Store 계약이 아니라 어댑터 계약의 일부입니다.

## cleanup 보장

`subscribe(listener)`는 unsubscribe 함수를 반환합니다. 추상화는 이 정리를 잊기 어렵게 만들어야 합니다.

좋은 어댑터 API는 보통 다음 중 하나를 합니다.

- `destroy()`나 `dispose()` 메서드를 반환합니다.
- 대상 런타임 생명주기에 cleanup을 등록합니다.
- teardown을 소유하는 controller에 구독 범위를 묶습니다.

```ts lineNumbers
const connection = connectStore(store);

try {
  runWithConnection(connection);
} finally {
  connection.destroy();
}
```

cleanup을 호출하면 해당 리스너의 이후 알림이 멈춰야 합니다. 또 이후 업데이트가 없더라도, 소유자가 끝났을 때 소비자가 cleanup을 호출해도 안전해야 합니다.

## 교체를 의식한 쓰기

`setState`는 전체 상태 값을 교체합니다. 라이브러리가 partial update를 노출한다면, 라이브러리가 `setState`를 호출하기 전에 필드를 병합해야 합니다.

```ts lineNumbers
function setPartial<T extends object>(store: Store<T>, partial: Partial<T>) {
  store.setState((prev) => ({ ...prev, ...partial }));
}
```

이 선택을 명확히 하세요. 어떤 라이브러리는 Store와 정확히 맞기 때문에 교체 쓰기를 노출하는 편이 좋습니다. 다른 라이브러리는 사용자에게 더 안전한 domain action이나 patch helper를 노출하는 편이 좋습니다.

## 호환성 체크리스트

어댑터나 라이브러리를 배포하기 전에 공개 계약을 따르는지 확인하세요.

- 어댑터가 `getState()`로 스냅샷을 읽습니다.
- public contract가 private 필드를 노출하거나 내부 리스너 저장소에 의존하지 않습니다.
- 모든 구독의 생명주기 소유권이 분명합니다.
- 스냅샷 업데이트가 리스너 안에서 새 상태를 읽습니다.
- cleanup이 반환되거나 등록되거나 다른 방식으로 보장됩니다.
- 호환성 메모가 쓰기 방식이 전체 교체인지, action 전용인지, 라이브러리가 병합하는 partial update인지 설명합니다.
- 여러 스토어 인스턴스를 테스트해 소비자 사이에 상태가 새지 않는지 확인합니다.
- 문서는 앱 사용자를 [프레임워크 사용법](./framework-usage)과 [공통 패턴](./patterns)으로 안내하고, 이 페이지는 어댑터 작성자에게 집중합니다.
