# @ilokesto/state

`@ilokesto/state` turns external store state into framework-native adapters. The package root is only the package boundary; actual APIs live under framework subpaths such as `@ilokesto/state/react`, `@ilokesto/state/vue`, and `@ilokesto/state/svelte`.

## What this package gives you

- **Framework adapters** for React, Vue, Angular, Svelte, and Solid.
- **One `create()` shape per adapter** for state objects, vanilla stores, or reducers.
- **Selector subscriptions** that keep framework reads narrow.
- **Imperative accessors** such as `writeOnly()` for work outside framework lifecycles.
- **Store middleware** for logging, persistence, validation, and debugging.

## What it intentionally does not give you

- No provider-first app structure.
- No Zustand-style initializer.
- No custom equality API for selectors.
- No root-level `create` export. Choose a framework subpath.

## Installation

```package-install
@ilokesto/state
```

## Quick Look

```tsx lineNumbers
import { create } from '@ilokesto/state/react';

const useCounter = create({ count: 0 });

function Counter() {
  const [count, setState] = useCounter((state) => state.count);

  return (
    <button onClick={() => setState((prev) => ({ ...prev, count: prev.count + 1 }))}>
      {count}
    </button>
  );
}
```

The shape is small:

- `create()` builds a framework adapter from external state,
- the selector decides what the framework subscriber reads,
- the writer still updates the full store state.

## Where it fits

Use framework-local state when one component owns the value. Use context/providers when many components need the same stable dependency. Reach for `@ilokesto/state` when several components need to subscribe to the same changing value and you want the store to stay outside the framework runtime.

That outside-framework boundary is the point. Actions, middleware, tests, and non-framework code can talk to the same state container, while each UI layer keeps its native adapter shape.
