# SSR 및 초기 상태

## 초기 스냅샷과 하이드레이션

`@ilokesto/state`의 SSR 지원은 브라우저에서 훅을 움직이는 것과 같은 계약에서 나옵니다.
훅은 React의 외부 store 구독 모델 위에 있으므로, React는 서버에서 렌더링할 때의 snapshot과 클라이언트에서 실행할 때의 snapshot을 각각 요청할 수 있습니다.

작아 보이는 차이지만 하이드레이션이 예측 가능한지를 결정합니다.
서버는 어떤 값으로 마크업을 렌더링합니다.
클라이언트는 그 마크업에 이벤트 핸들러를 붙이고, 첫 클라이언트 읽기가 서버 결과와 맞는지 확인합니다.
값이 맞지 않으면 React가 hydration mismatch를 보고하거나 렌더링된 트리 일부를 교체할 수 있습니다.

유용한 규칙은 다음과 같습니다.

- `getState()`는 "store 값이 지금 무엇인가?"에 답합니다.
- `getInitialState()`는 "이 store가 어떤 값으로 시작했는가?"에 답합니다.

둘은 다른 질문입니다.
store가 `{ count: 0 }`으로 시작한 뒤 write를 받으면 `getState()`는 `{ count: 1 }`을 돌려줄 수 있습니다.
그래도 초기값은 여전히 `{ count: 0 }`입니다.

`@ilokesto/state`는 server snapshot 경로에서 `store.getInitialState()`를 사용합니다.
그래서 서버 렌더링은 이후의 클라이언트 변경이 아니라 생성자 시점의 값에 묶입니다.
SSR 코드를 설계할 때 초기값을 편리한 기본값이 아니라 렌더링 계약의 일부로 다루세요.

## 서버와 클라이언트 스냅샷

React의 외부 store 계약에는 여기서 중요한 snapshot 읽기가 두 개 있습니다.
client snapshot은 앱이 실행된 뒤 사용하는 live 값입니다.
server snapshot은 서버에서 HTML을 렌더링할 때와 첫 hydration pass를 확인할 때 React가 사용하는 값입니다.

`@ilokesto/state`에서는 이 구분이 store 메서드와 명확하게 맞습니다.

```ts lineNumbers
const useCounter = create({ count: 0 });

const current = useCounter.getState();
const initial = useCounter.getInitialState();
```

`getState()`는 현재 live 값을 돌려줍니다.
write 이후에는 값이 바뀝니다.
event handler, action, effect, test, 최신 store 값이 필요한 코드에서 사용합니다.

`getInitialState()`는 store가 만들어질 때 캡처된 값을 돌려줍니다.
두 번째 live store가 되는 것이 아닙니다.
시작점을 안정적으로 설명하는 값입니다.

SSR 동안 훅은 `store.getInitialState()`를 server snapshot으로 제공합니다.
즉 서버에서 렌더링된 컴포넌트는 그 요청을 위해 store가 만들어진 값과 같은 shape, 같은 값을 보아야 합니다.
클라이언트가 같은 초기 데이터로 store를 만들면 하이드레이션도 같은 snapshot에서 시작합니다.

그래서 초기 데이터는 명시적이어야 합니다.
서버가 request data로 store를 만들었다면, 클라이언트도 대응되는 store를 만들 때 같은 직렬화된 request result가 필요합니다.
하이드레이션 뒤 client effect가 "따라잡는" 방식에 기대지 마세요.
effect는 첫 렌더를 보호하기에는 너무 늦게 실행됩니다.

## 요청별 스토어

서버 코드는 하나의 프로세스 생명주기 안에서 많은 사용자를 처리합니다.
그래서 SSR에서 module level state는 위험합니다.
singleton store는 request A의 데이터를 유지한 채 request B를 렌더링할 때 노출할 수 있습니다.

브라우저 탭에서는 module이 한 사용자 세션에 속하므로 이 패턴이 안전할 수 있습니다.
하지만 서버 기본 패턴으로는 안전하지 않습니다. module이 요청 사이에서 공유될 수 있기 때문입니다.

요청마다 새 store를 만드는 factory를 선호하세요.

```ts lineNumbers
import { create } from '@ilokesto/state/react';

type ViewerState = {
  viewerId: string | null;
  theme: 'light' | 'dark';
};

export function createViewerStore(initialState: ViewerState) {
  return create(initialState);
}
```

그런 다음 request scoped code에서 factory를 호출합니다.

```tsx lineNumbers
import { createViewerStore } from './viewer-store';

type PageProps = {
  viewer: {
    id: string;
    theme: 'light' | 'dark';
  } | null;
};

export default function Page({ viewer }: PageProps) {
  const initialState = {
    viewerId: viewer?.id ?? null,
    theme: viewer?.theme ?? 'light',
  };

  const useViewer = createViewerStore(initialState);

  return <ViewerPanel useViewer={useViewer} />;
}
```

이 예시는 framework adapter를 새로 만들지 않습니다.
중요한 경계만 보여줍니다. request data가 initial object가 되고, 그 object가 factory를 통해 `create()`로 들어갑니다.

React Server Components에서는 서버 컴포넌트에서 클라이언트 컴포넌트로 hook 자체를 넘기지 마세요. 경계를 넘기는 값은 직렬화 가능한 plain `initialState`로 두고, 클라이언트 컴포넌트 안에서 one-time initializer로 hook을 만드세요.

나쁜 모양은 모든 요청에서 재사용되는 서버 singleton입니다.

```ts lineNumbers
import { create } from '@ilokesto/state/react';

export const useViewer = create({
  viewerId: null,
  theme: 'light',
});
```

이 singleton은 순수 client side state에는 괜찮을 수 있습니다.
사용자별 데이터가 있는 서버 렌더링에서는 leak risk를 만듭니다.
한 요청이 store를 write한 뒤 다른 요청이 렌더링될 수 있습니다.
렌더 중 write하지 않는다고 해도, 이후 유지보수에서 singleton이 실수로 공유 mutable cache가 될 수 있습니다.

## 하이드레이션 불일치

하이드레이션은 서버 렌더 결과와 첫 클라이언트 렌더를 비교합니다.
가장 안전한 길은 단순합니다. 서버 마크업을 만든 초기 상태와 같은 초기 상태로 클라이언트 store를 만드세요.

이 코드는 안전합니다.

```tsx lineNumbers
const initialState = {
  viewerId: 'user-123',
  theme: 'dark',
};

const useViewer = create(initialState);
```

이 코드는 위험합니다.

```tsx lineNumbers
const useViewer = create({
  viewerId: null,
  theme: 'light',
});

useViewer.setState({
  viewerId: 'user-123',
  theme: 'dark',
});
```

두 번째 예시는 결국 올바른 live state에 도달할 수 있지만, 같은 snapshot에서 시작하지 않습니다.
첫 렌더는 서버가 만든 signed in dark mode 마크업 대신 anonymous light mode 마크업을 보여줄 수 있습니다.
수정이 자리 잡기 전에 React는 다른 트리를 보게 됩니다.

초기 렌더에서 browser only data를 읽을 때도 같은 문제가 생길 수 있습니다.
예를 들어 `localStorage`에 저장된 theme은 서버 렌더링 중에는 사용할 수 없습니다.
서버 마크업은 `light`를 가정하고 첫 클라이언트 렌더는 `dark`를 가정하면, 앱은 서로 다른 두 답으로 시작합니다.

첫 렌더의 source를 하나로 정하세요.
서버가 첫 답을 소유한다면 그 답을 직렬화하고 클라이언트 store도 그 값으로 만드세요.
브라우저가 첫 답을 소유한다면 브라우저 값을 알 때까지 안정적인 placeholder를 렌더링하세요.
명시적인 규칙 없이 둘을 섞지 마세요.

### 흔한 첫 렌더 함정

다음 값들은 서버와 브라우저가 첫 렌더 동안 같은 답을 줄 수 없어서 mismatch를 만들기 쉽습니다.

- 초기 상태에서 사용하는 `Date.now()` 또는 `new Date()`,
- ID나 기본값에 쓰는 `Math.random()`,
- 초기 렌더 중 읽는 `window`, `document`, `localStorage`, media query,
- hydration 전에 request state를 대체하는 persisted state,
- 사용자별 서버 데이터를 담은 module-level singleton.

이런 읽기는 명시적인 경계 뒤로 옮기세요. 서버가 값을 직렬화한 initial state로 넘기거나, 안정적인 client-only placeholder를 렌더링한 뒤 mount 후에 업데이트합니다.

```tsx lineNumbers
function ClientOnlyTheme() {
  const [ready, setReady] = useState(false);

  useEffect(() => {
    setReady(true);
  }, []);

  if (!ready) return <ThemeShell theme="light" />;

  const theme = readThemeFromLocalStorage();
  return <ThemeShell theme={theme} />;
}
```

placeholder는 첫 클라이언트 렌더를 서버와 맞춰 줍니다. 브라우저 전용 값은 React가 제어권을 가진 뒤에 나타납니다.

## 부트스트랩 패턴

bootstrap pattern은 서버와 클라이언트 경계에서 초기값을 눈에 보이게 만듭니다.
서버는 plain JSON을 준비합니다.
클라이언트는 그 JSON을 읽고 같은 store factory에 넘깁니다.

Next.js style 설정에서는 모양을 단순하게 유지할 수 있습니다.

```tsx lineNumbers
// app/account/page.tsx
import { AccountClient } from './account-client';

export default async function AccountPage() {
  const viewer = await loadViewerForRequest();

  const initialState = {
    viewerId: viewer?.id ?? null,
    displayName: viewer?.displayName ?? 'Guest',
  };

  return <AccountClient initialState={initialState} />;
}
```

```tsx lineNumbers
// app/account/account-client.tsx
'use client';

import { useState } from 'react';
import { createAccountStore } from './account-store';

type AccountState = {
  viewerId: string | null;
  displayName: string;
};

type AccountClientProps = {
  initialState: AccountState;
};

export function AccountClient({ initialState }: AccountClientProps) {
  const [useAccount] = useState(() => createAccountStore(initialState));

  return <AccountView useAccount={useAccount} />;
}
```

이 예시는 일반 component props를 bootstrap channel로 사용합니다.
package 전용 provider나 숨겨진 global이 필요하지 않습니다.
핵심은 `initialState`가 서버에서 클라이언트 경계를 안전하게 건널 수 있는 plain object라는 점입니다.
클라이언트 컴포넌트는 hook을 한 번만 만들기 때문에, 리렌더가 store를 초기화하지 않습니다.

앱이 커지면 factory를 framework file과 분리하세요.

```ts lineNumbers
import { create } from '@ilokesto/state/react';

export type AccountState = {
  viewerId: string | null;
  displayName: string;
};

export function createAccountStore(initialState: AccountState) {
  return create(initialState);
}
```

이렇게 하면 test, server file, client file이 store를 만드는 하나의 공유 방식을 갖습니다.
또 초기 상태 type이 명시되어 서버와 클라이언트가 서로 어긋나는 일을 줄입니다.

## 영속화와 SSR 충돌

persistence는 첫 렌더에 또 다른 질문을 추가합니다.
서버는 하나의 initial state를 제공할 수 있고, 브라우저에는 이전 방문에서 남은 오래된 persisted state가 있을 수 있습니다.
두 값이 모두 유효할 수 있지만, 둘 다 동시에 하이드레이션을 소유할 수는 없습니다.

서버가 다음 값을 렌더링한다고 가정해 보세요.

```ts lineNumbers
const serverInitialState = {
  viewerId: 'user-123',
  displayName: 'Ari',
};
```

브라우저에는 다음 값이 local에 저장되어 있을 수 있습니다.

```ts lineNumbers
const persistedState = {
  viewerId: 'user-123',
  displayName: 'Old Name',
};
```

persistence가 하이드레이션 전에 store를 교체하면, 클라이언트는 서버 마크업의 `Ari` 대신 `Old Name`을 렌더링할 수 있습니다.
두 state가 같은 사용자에 속해도 mismatch입니다.

persistence를 SSR page에 연결하기 전에 precedence rule을 정하세요.

1. server initial state가 hydration에서 이기고, persisted state는 나중에 merge될 수 있습니다.
2. persisted state는 client only gate가 안정적인 fallback을 렌더링한 뒤에만 이깁니다.
3. 일부 field는 서버에서 오고, local preference는 persistence에서 옵니다.

첫 번째 규칙은 identity, permission, server loaded record 같은 request scoped data에 보통 가장 안전합니다.
세 번째 규칙은 collapsed panel이나 draft UI setting 같은 local preference에 잘 맞습니다.

분리를 명시적으로 유지하세요.

```ts lineNumbers
type AccountState = {
  viewerId: string | null;
  displayName: string;
  sidebarCollapsed: boolean;
};
```

이 shape에서는 `viewerId`와 `displayName`이 server initial state에서 오고, `sidebarCollapsed`는 client가 시작된 뒤 복원될 수 있습니다.
persistence가 SSR과 맞지 않는다는 뜻은 아닙니다.
persisted state도 또 하나의 source of truth이므로, timing과 precedence rule이 분명해야 한다는 뜻입니다.

규칙이 불분명할 때는 `getInitialState()`를 서버 렌더 snapshot의 anchor로 사용하고, persisted override는 하이드레이션 뒤로 미루세요.
그러면 첫 클라이언트 렌더가 서버 출력과 맞고, React가 제어권을 얻은 뒤에도 브라우저의 local preference를 복원할 수 있습니다.
