# Persist

`persist` saves store state to browser storage and restores it when the store starts again. It keeps the in-memory store and the selected storage target in sync.

## Usage

Apply `persist` to a store object, or use it as a curried middleware factory while creating a store.

```ts lineNumbers
import { persist } from '@ilokesto/state/middleware';

const store = persist({ local: 'counter-storage' })({ count: 0 });
```

## Storage Configuration

The configuration object accepts three storage targets:

- **`local`**: (string) The key name for `localStorage`. Use it for data that should survive browser restarts.
- **`session`**: (string) The key name for `sessionStorage`. Use it for data that should disappear when the tab closes.
- **`cookie`**: (string) The key name for cookie storage. Use it for small pieces of state that the server may need to read.

## The Rehydration Flow

A store initialized with `persist` restores saved state before normal use:
1. **Initial state**: The store starts with the provided initial state.
2. **Synchronous read**: The middleware immediately reads persisted state from the configured storage target.
3. **Replacement**: If the stored data is valid, the restored state becomes the current store state.
4. **Referential-change guard**: The store reference changes only when the restored state differs from the initial state.

## Storage Shape and Versioning

Persisted data is stored in a wrapper object:
```json lineNumbers
{
  "state": { ... },
  "version": 2
}
```

- **Version derivation**: The current `version` comes from the length of the `migrate` chain. Three migration functions produce version `3`.
- **Write-through behavior**: After every store commit, the middleware writes the new state to storage.
- **Write cache**: The middleware caches the encoded persisted payload and skips storage writes when the next encoded value is identical.

## Migrations

The `migrate` option accepts an array of functions that transform old state shapes into the current shape.

- **Target limitations**: Migrations are supported for `local` and `cookie` targets. `session` storage does not support migrations.
- **Incremental updates**: Each function in the array represents one version step. If the stored version is `1` and the current chain length is `3`, functions `[1]` and `[2]` run in order.

## Cookie Limitations

The `cookie` target has browser limits:
- **Size**: Cookies are usually limited to 4KB. Large state trees will fail to persist.
- **Serialization**: Data is JSON serialized. Keep state free of circular references and non-serializable objects such as functions or classes.

## Middleware Ordering

The position of `persist()` in the middleware chain changes what gets saved.

**Recommended order**: Place `persist()` near the end of the chain.
Then middleware such as `validate` or `debounce` can handle the update first, and `persist` saves the final state.

```ts lineNumbers
const store = pipe(
  validate(schema),
  persist({ local: 'app-state' })
)({ count: 0 });
```
